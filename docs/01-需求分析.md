# TaskFlow 分布式异步任务调度平台 —— 需求分析

## 一、背景与动机（Why）


### 实习场景来源（真实动机）

本项目的立项动机来源于一段真实实习经历：

> 实习中接触的是一套**部署在单节点上的多级任务队列**，用于「音频转写 → 质检」的流水线处理。队列结构为：
>
> ```
> 转写排队队列 → 转写任务队列 → 质检排队队列 → 质检任务队列
> ```
>
> 四个队列构成一条「转写 → 质检」的两级流水线，每级又分为「排队队列（缓冲等待）+ 任务队列（实际执行）」。其中：
>
> - **队列元素是任务对象**（封装了音频 ID、文件路径等业务数据），由线程池中的线程消费执行；
> - 真正**完成任务的服务运行在其他节点**，通过消费队列来执行转写 / 质检。

这套实习方案虽然能跑通业务，但存在明显的架构局限：

| 局限 | 说明 |
|---|---|
| **单点故障** | 四个队列全部托管在同一个节点上，该节点宕机则整条流水线不可用 |
| **瓶颈集中** | 队列节点成为吞吐与可靠性的集中瓶颈 |
| **流水线硬编码** | 「转写 → 质检」的流程被写死，难以扩展到其他任务类型 |
| **伸缩性弱** | worker 虽在其他节点，但队列本身无法横向扩展 |

因此，本项目的目标是：**保留实习中「多级队列 + 任务对象 + 队列与执行分离」的核心思想，将其从单节点内存队列升级为基于消息中间件的分布式、可插拔、可横向扩展的通用任务调度平台。**

### 项目定位：通用调度平台 + 一个真实场景落地

项目的关注点是**任务生命周期的可靠性与高并发效率**，而非具体业务实现。因此定位分两层：

| 层次 | 内容 | 价值 |
|---|---|---|
| **框架层** | 通用、可插拔、聚焦可靠性 / 高并发 | 技术深度 |
| **示例层** | 通知推送（高并发 + 强幂等），实现 mock | 证明能落地 |

**为什么选通知推送作为落地场景**：它几乎把平台的每个能力都天然用到——

| 平台能力 | 在通知推送里的体现 |
|---|---|
| 高并发 | 一次给百万用户推送，瞬间百万任务 |
| 幂等（最重要） | 同一条短信绝不能发两次（真实事故） |
| 重试 / 死信 | 短信网关会超时 / 失败 |
| 优先级 | 验证码（高优）> 营销短信（低优） |
| 延迟队列 | 定时推送 |
| 限流 | 短信网关有 QPS 限制，worker 必须限速消费 |
| 批量 | 一次营销活动 = 一个批次 |
| 超时兜底 | 推送超时未回执 → 标记 / 重推 |

**任务类型设计（可扩展）**：

| task_type | 类型 | 说明 |
|---|---|---|
| `SEND_SMS` | 真实场景 | 发送短信（验证码 / 营销的区分靠 priority 字段，不靠 task_type） |
| `MOCK_TASK` | 模拟压测 | sleep + 随机失败，纯压测，验证框架性能 |

> 关键设计：**不用 task_type 表达优先级**——任务类型表达「做什么」，优先级由独立的 `priority` 字段表达「多急」，两者正交。

## 二、目标用户与角色

| 角色 | 诉求 |
|---|---|
| 业务方 / 开发者 | 提交任务、动态注册执行器、查询进度与结果 |
| 平台管理员 | 监控任务堆积、失败告警、执行器扩缩容 |
| 系统 | 稳定性、可观测、可扩展 |

## 三、核心需求（功能需求）

### 1. 任务生命周期管理
- 提交任务（支持批量，即「批次」）。
- 任务状态流转与查询（列表 + 详情 + 进度）。
- 任务取消、失败重试。
- 任务结果回传与查询。

### 2. 任务调度与执行
- 任务入队、多节点消费执行（横向扩展）。
- 执行器可插拔（不同任务类型走不同 handler，如转写 / 质检 / 导出）。
- 失败自动重试（次数可配）。
- 超时任务兜底（延迟队列检查）。
- 优先级调度。
- 流水线流转（如「转写完成 → 自动触发质检」）。

### 3. 平台稳定性（非功能需求）
- 消息不丢、不重复执行（幂等）。
- 任务落库与发送消息的一致性。
- 高并发下的限流、削峰。
- 可观测（任务状态、失败原因、执行耗时、队列堆积）。

## 四、非功能需求（性能指标基线）

> 这些指标作为后续优化「前后对比」的基线。

| 指标 | 目标值 |
|---|---|
| 任务提交接口 | 峰值吞吐 ≥ X 提交 / 秒，P99 响应 < 300ms |
| 任务执行 | 支持 N 个 worker 实例横向扩展 |
| 消息可靠性 | 不丢、不重（幂等保证） |
| 数据库查询 | 列表页 P99 < 100ms（500 万条数据量） |
| 可用性 | 单节点宕机不影响整体 |

## 五、核心业务流程

```
用户 / 业务方
   │
   ▼
提交任务 ──► 参数校验 ──► 任务落库(待处理)
   │                         │
   │              本地消息表(同事务) ◄── 一致性关键
   │                         │
   │                         ▼
   │                     发消息到 MQ
   │                         │
   ▼                         ▼
返回 taskId           Worker 消费
                         │
                   分布式锁 + 幂等校验
                         │
                         ▼
                      线程池执行
                         │
               ┌─────────┴──────────┐
               ▼                    ▼
            成功                   失败
               │                    │
         更新状态(成功)        重试次数 + 1
         回传结果               │
               │         ┌───────┴───────┐
               ▼         ▼               ▼
           用户查询   未超 N 次继续重试   超 N 次进死信队列
                                                   │
                                             人工介入 / 告警
```

### 关键闭环

- **提交阶段**：落库 + 消息表在同一个本地事务，保证「任务一定能发出去」。
- **执行阶段**：消费靠幂等 + 状态机，保证「任务只执行一次」。
- **兜底阶段**：延迟队列扫描超时未完成的任务，做标记或重发。

## 六、需求拆解成模块 / 边界

| 模块 | 职责 | 对应需求 |
|---|---|---|
| 网关 gateway | 鉴权 + 限流 | 高并发入口 |
| 任务中心 task-center | 任务 / 批次 CRUD、状态机、查询 | 生命周期管理 |
| 任务生产者 producer | 校验、落库、发消息、本地消息表 | 一致性 |
| 任务执行器 worker | 消费、幂等、线程池执行、回调 | 调度执行 |
| 公共 common | 统一返回、异常、幂等注解、分布式 ID | 横切 |

> 说明：任务「提交 + 落库 + 发消息」在多模块拆分时可合并进 task-center，也可独立为 producer，具体拆分原则见《02-架构与部署》。

## 七、技术选型分析（锁定「为什么」）

### 1. 消息中间件：为什么选 RabbitMQ

**三大主流候选对比**：

| 维度 | RabbitMQ | Kafka | RocketMQ |
|---|---|---|---|
| 定位 | 企业级消息队列 | 高吞吐日志 / 流处理 | 金融级可靠消息 |
| 消息模型 | Exchange/Queue 灵活路由 | Topic/Partition | Topic/Queue |
| 延迟消息 | ✅ TTL + 死信队列原生支持 | ❌ 需额外处理 | ✅ 原生延迟消息 |
| 手动 ACK | ✅ 天然支持 | ❌ 偏移量机制，不适合逐条精确 ACK | ✅ 支持 |
| 吞吐量 | 万级 / 秒 | 百万级 / 秒 | 十万级 / 秒 |
| 单条可靠性 | 高 | 高（但侧重批量） | 高 |

**选 RabbitMQ 的核心理由**（贴合 TaskFlow 场景）：

1. **延迟队列 + 死信队列原生支持**：TaskFlow 的「失败重试、超时兜底」直接靠 TTL + DLX 实现，不用自己造轮子。
2. **手动 ACK 机制完善**：任务必须「执行成功才确认」，这是任务调度的刚需；Kafka 的 offset 提交模型做逐条精确确认很别扭。
3. **灵活路由（Exchange）**：可按任务类型、优先级路由到不同队列，天然契合「可插拔执行器」「多级队列」的设计。
4. **权重在「可靠投递」而非「极限吞吐」**：任务平台对「每条消息不能丢、不能重」的要求，高于「每秒百万条」的吞吐要求，选 RabbitMQ 是抓对主要矛盾。

> 选型结论话术：**「我选 RabbitMQ 是因为 TaskFlow 属于『可靠逐条处理』场景，而非『海量吞吐』场景，这是区分消息中间件选型的核心判断。」**

### 2. 缓存 / 协调：为什么用 Redis

Redis 在 TaskFlow 里承担 3 个 MySQL 替代不了的角色：

1. **分布式锁（Redisson）**：多 worker 防重复执行；MySQL 的行锁 / 乐观锁是单库内的，跨进程防重必须靠 Redis 这类分布式协调组件。
2. **热点缓存**：任务结果、频繁查询的热点数据，Redis 读延迟亚毫秒级，能挡掉大量重复查询，避免打穿数据库。
3. **高并发计数 / 临时状态**：队列长度、失败次数、限流计数器（令牌桶），用 Redis 原子操作（INCR / Lua）高效且不污染主库。

**为什么不用本地缓存**：TaskFlow 是分布式多实例，本地缓存会导致各节点数据不一致，Redis 是集中式共享缓存，天然适合分布式场景。

**对比 Zookeeper**：ZK 偏强一致 / 协调，性能不如 Redis，且做「短临界区互斥锁」场景 Redis 足够，引入成本更低。

> 选型结论话术：**「Redis 兼具『缓存 + 分布式锁 + 原子计数』三种能力，一个组件覆盖三个需求，引入成本最低。」**

### 3. 一致性方案：为什么选本地消息表（而非 Seata 2PC / 事务消息）

这是「任务落库 + 发 MQ 一致性」的选型，三种方案对比：

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **本地消息表** | 业务和消息同库同事务，定时扫描补发 | 实现简单、不依赖特定 MQ、直观可查 | 有延迟（依赖定时扫描）、需额外表 |
| 事务消息（RocketMQ） | MQ 预发 + 回查机制 | 实时性好、无额外表 | 强绑定 RocketMQ，可移植性差 |
| Seata 2PC | 全局事务协调 | 强一致 | 性能开销大、长事务占锁，适合金融级强一致 |

**选本地消息表的理由**：

1. **与 MQ 解耦**：不绑定 RocketMQ，换 Kafka / RabbitMQ 都可，可移植性好。
2. **实现可控、可观测**：消息状态（待发送 / 已发送 / 已确认）落库，出问题能直接查表定位，比黑盒的 MQ 事务更直观。
3. **契合「任务」语义**：任务本身就要落库持久化，天然有「业务表 + 消息表」共存的条件，加一张消息表成本极低。
4. **性能取舍合理**：牺牲一点实时性（定时扫描几十毫秒到秒级），换来简单和可靠。

> 选型结论话术（与 Seata 形成对比）：**「下单是要强一致的金融动作，我用 Seata 2PC；而任务发消息是允许短暂延迟的最终一致，用本地消息表更轻量、性能更好。强一致用 2PC、最终一致用消息表，这是选型的分界。」**

### 4. 服务注册 / 配置中心：为什么用 Nacos

| 候选 | 特点 |
|---|---|
| Nacos | 注册中心 + 配置中心二合一，支持健康检查、权重、动态配置 |
| Eureka | 老牌，但已停止维护 |
| Zookeeper | 偏 CP 强一致，做注册中心性能一般且运维复杂 |
| Consul | 功能全，但国内生态、文档不如 Nacos |

**选 Nacos 理由**：注册发现 + 健康监测（异常剔除）+ 负载均衡 + 配置共享，一个组件覆盖服务治理的全部需求，且与 Spring Cloud Alibaba 生态无缝集成。

### 5. 网关：为什么选 Spring Cloud Gateway（而非 Zuul）

| 维度 | Spring Cloud Gateway | Zuul |
|---|---|---|
| 底层 | WebFlux / Netty（非阻塞） | Servlet（阻塞） |
| 性能 | 高并发下更优 | 较弱 |
| 维护 | Spring 官方主推 | 已边缘化 |

**选 Gateway 理由**：非阻塞响应式，适合高并发统一入口，天然支持限流（内置 RequestRateLimiter + Redis）、路由、全局过滤器（JWT 鉴权），与「入口限流 + JWT」的需求完美契合。

### 6. 服务通信：OpenFeign + RabbitMQ 双通道

**同步用 OpenFeign、异步用 RabbitMQ**，服务通信的两条腿：

| 场景 | 方式 | 理由 |
|---|---|---|
| 实时查询结果、需要立即返回 | OpenFeign（同步 RPC） | 需要立即拿到返回，逻辑清晰 |
| 清购物车、消息通知、超时处理 | RabbitMQ（异步） | 解耦、削峰、容忍延迟，失败可重试 |

> 选型原则话术：**「服务间通信我遵循『同步响应用 Feign、异步解耦 / 削峰用 MQ』的原则，根据业务是否需要立即返回结果来选，而不是一刀切。」**

### 7. 数据库：MySQL + 主从读写分离

- **为什么 MySQL 而非 NoSQL**：任务数据是强结构化的关系型数据（任务、批次、消息表存在强关联和事务需求），MySQL 的事务（本地消息表依赖事务）和成熟的主从复制是刚需。
- **读写分离**：任务写入频繁、查询 / 统计也频繁，主从分离让读流量走从库，缓解主库压力，是分布式系统标配。

### 8. 锁选型：乐观锁 / 悲观锁 / 分布式锁按场景

| 场景 | 锁类型 | 理由 |
|---|---|---|
| 任务状态更新（单库内并发） | 乐观锁（版本号） | 读多写少、冲突概率低，性能好 |
| 跨节点防重复执行 | Redisson 分布式锁 | 跨进程互斥，MySQL 锁无法覆盖 |
| 金融扣款等高冲突场景 | 悲观锁 | 冲突概率高，需强串行化 |

## 八、风险与边界

- **不做**：任务编排 DAG（如 XXL-Job 的复杂工作流），一期只做「有向的简单流转」，控制范围。
- **边界**：执行器只负责执行，任务的业务校验在生产端（提交侧）做。
- **风险**：消息堆积、单点热点（分布式 ID 时钟回拨）、主从延迟——这些将作为后续技术攻关点逐一解决。

## 需求分析小结

需求分析至此完成了「为什么做、做什么、给谁做、怎么做、边界在哪」的完整闭环。下一步衔接的核心设计产出为：

1. 任务状态机定义（状态 + 流转规则 + 每个状态允许的操作）。
2. 核心表结构 + 索引设计（服务于数据库优化）。
3. 接口清单 / API 设计。
