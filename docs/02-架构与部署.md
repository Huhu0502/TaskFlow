# TaskFlow 分布式异步任务调度平台 —— 架构与部署

## 一、两个概念先行（面试易混，答清加分）

| 层面 | 含义 | 回答要点 |
|---|---|---|
| **微服务（逻辑模块）** | 代码 / 职责的拆分，一个服务一份代码一个进程 | 有几种「服务类型」 |
| **节点 / 实例（物理部署）** | 每个服务实际起的进程数量 | 一个服务可起多个实例 |

面试问「部署几个微服务」，两层都要答：**有几种服务 + 每种部署了几个实例**。

## 二、实际资源约束

本项目是个人学习 / 实践项目，真实可用资源只有 **2 台机器**：

| 机器 | 定位 | 说明 |
|---|---|---|
| 笔记本（本机） | 开发 + 部分部署 | 写代码、调试、跑单测 |
| 远程服务器（1 台） | 主力部署 | 中间件 + 业务服务 |

因此部署方案必须务实：**中间件单机跑、业务服务单实例起步，横向扩展靠增加进程数，而不是增加物理机。**

## 四、服务清单（逻辑拆分）

| 序号 | 服务 | 职责 | 是否必须独立 |
|---|---|---|---|
| 1 | **gateway** | 鉴权、限流、路由转发 | 必须 |
| 2 | **task-center** | 任务 / 批次 CRUD、状态机、进度查询、统计分析 | 必须 |
| 3 | **producer** | 校验、落库、本地消息表、发 MQ | **可选合并**进 task-center |
| 4 | **worker** | 消费 MQ、幂等、线程池执行、回传结果 | 必须（需多实例） |

### 关键设计决策：producer 不单独拆开

任务「提交 + 落库 + 发消息」合并进 task-center，不独立成 producer 服务。理由：

1. **本地消息表的本质要求**：任务的「落库」和「消息表写入」必须在**同一个数据库事务**里，而发消息也要紧邻这个事务。拆成独立服务会打破「同库同事务」，被迫引入跨服务事务，属于过度设计。
2. **降低复杂度**：前期任务量不大，提交和查询放在一个服务，链路短、易排查。
3. **演进空间**：等后期任务量大、提交与查询相互干扰时，再把「提交 + 发消息」拆为独立 producer 服务。

> 面试话术：**「我没有单独拆 producer，而是合并在 task-center 里，因为本地消息表要求『任务落库』和『发消息』在同一个数据库事务里，拆开反而要引入跨服务事务，前期属于过度设计。」**

## 五、worker 设计：按任务类型拆分服务，每类型 1 实例起步

**关键点**：worker **按任务类型拆分为独立服务**（每个类型一个 worker 服务），不同类型天然隔离，互不影响；由于任务均为**简单、执行快、可重试的轻量任务**，**每个类型的 worker 只需 1 个实例**。

```
                  ┌── 转写队列 ──► [转写 worker]（1 实例）
                  │
task-center ──────┼── 质检队列 ──► [质检 worker]（1 实例）
  （按类型路由）    │
                  └── 导出队列 ──► [导出 worker]（1 实例）
```

### 设计取舍

| 维度 | 设计 | 理由 |
|---|---|---|
| 队列 | 按类型分队列 | 不同类型任务走不同执行器，路由清晰 |
| worker 服务 | 按类型分服务 | 类型独立、故障隔离，单个类型异常不影响其他类型 |
| 实例数 | 每类型 **1 个** | 任务简单、执行快，单实例吞吐足够 |
| 扩展方式 | 某类型量大时**只给该类型加进程** | 扩展粒度精细到类型级别，不需要整体扩容 |

### 扩展策略（两层）

1. **职责维度扩展**：按任务类型拆分 worker 服务，天然隔离、互不影响；
2. **容量维度扩展**：`每类型 1 个`是当前资源配置，架构本身支持按类型单独加进程，精准扩容。

> 面试话术：**「我的扩展策略分两层：一是按任务类型拆分 worker 服务，不同类型天然隔离，这是职责维度的扩展；二是每种类型的 worker 进程数是弹性的——任务简单、执行快，正常情况下单实例够用，一旦某类任务量大，我只给那类 worker 加进程，不需要整体扩容。所以『每个类型 1 个』是当前资源配置，不是架构上限。」**

### ⚠️ 重要提醒：单实例仍需幂等 + 分布式锁

「每个类型只有 1 个实例」**≠「不会重复执行」**。即使只有单实例，重复执行依然可能发生：

```
转写 worker（唯一实例）转写 taskId=123
   ↓ 执行到一半，ACK 超时
RabbitMQ 重新投递 taskId=123
   ↓ 还是这个唯一的 worker 重新消费到
同一个任务被同一个 worker 执行了两次！
```

- 单实例只是减少了「多实例并发竞争」这个重复源；
- 但「消息重投」「超时补偿」两个重复源依然存在，与实例数量无关。

> 面试话术：**「单实例只是减少了『多实例并发竞争』这个重复源，但『消息重投』和『超时补偿』两个重复源依然存在，所以幂等和分布式锁是必须的，与实例数量无关。」**

### 5.1 worker 内部设计：策略模式（待实现）

**关键认知**：worker 按类型拆服务，解决的是「服务之间」的职责划分；而 worker 服务**内部**的算法变体（如不同音频格式、不同 ASR 引擎/厂商），用**策略模式**解决。两者是不同层面，可以共存。

```
服务层（按类型拆微服务）：
  转写 worker  ┃  质检 worker  ┃  导出 worker
      │ 服务内部有算法变体时，用策略
      ▼
策略层（服务内部按算法选 Executor）：
  转写 worker 内部：
    ├── Mp3TranscribeExecutor
    ├── WavTranscribeExecutor
    ├── VendorATranscribeExecutor
    └── VendorBTranscribeExecutor
```

**是否需要策略的判断标准**：

| worker 内部情况 | 是否用策略 |
|---|---|
| 只有一种执行逻辑，无分支 | ❌ 不用（服务拆分已足够） |
| 有「不同格式/引擎/厂商」等子类型分支 | ✅ 用 |
| 未来可能新增执行方式，不想改旧代码 | ✅ 用（开闭原则） |

**三层对应关系**：

| 角色 | 落点 | 职责 |
|---|---|---|
| **执行器 Executor** | worker 内部的 `XxxExecutor`（策略接口 + 实现） | 执行具体算法 |
| **管理器 Manager** | worker 内部的 `ExecutorFactory` | 按子类型查找执行器（Spring 集合注入 Map） |
| **编排器 Orchestrator** | 跨服务（转写完成→触发质检） | 编排流程（发消息/事件） |

**实现结构（转写 worker 为例）**：

```java
// 策略接口
public interface TranscribeExecutor {
    TranscribeType supportType();
    String transcribe(Task task);
}

// 策略实现
@Component
public class DefaultTranscribeExecutor implements TranscribeExecutor {
    public TranscribeType supportType() { return TranscribeType.DEFAULT; }
    public String transcribe(Task task) { /* 默认转写 */ }
}

// 管理器（Spring 集合注入，无 if-else）
@Component
public class TranscribeExecutorFactory {
    private final Map<TranscribeType, TranscribeExecutor> map = new HashMap<>();
    public TranscribeExecutorFactory(List<TranscribeExecutor> list) {
        for (TranscribeExecutor e : list) map.put(e.supportType(), e);
    }
    public TranscribeExecutor get(TranscribeType type) { return map.get(type); }
}

// worker 主流程：无 if-else
@Component
public class TranscribeWorker {
    @Autowired private TranscribeExecutorFactory factory;
    public void onMessage(Task task) {
        factory.get(decideType(task)).transcribe(task);
    }
}
```

> **现阶段策略**：每种类型先写一个默认实现，但**接口先留好**（为扩展 + 面向接口编程 + 面试体现设计能力）。

## 七、中间件「设计集群、部署单机」的处理

这是最需要说清楚的一点：**生产环境要集群，但 2 台机器跑不了真集群。**

| 组件 | 生产设计（面试讲） | 本地实际（2 台机器） |
|---|---|---|
| MySQL | 主从读写分离 | 单实例，代码预留读写分离切换开关 |
| Redis | 主从 + 哨兵 | 单实例 |
| RabbitMQ | 集群 + 镜像队列 | 单实例（消息持久化即可） |
| Nacos | 3 节点集群 | 单机模式（standalone） |

> 面试话术：**「生产环境这些中间件都要做集群保证高可用，但本地学习环境只有 2 台机器，我采用『设计上集群、部署上单机』的方式——用单机模式跑通，但架构文档和代码里预留了集群部署方案。集群化只是运维配置，不影响业务代码。」**

**这段话说好了是加分项**，体现了「理解生产要集群，但清楚本地资源限制，能区分理想架构和现实落地」，比死背「所有组件都集群」更真实可信。

## 八、为什么这样部署（面试追问标准答案）

**Q1：为什么 worker 按类型拆分、每类型 1 个实例？**
> 不同类型任务执行器不同、逻辑独立，拆开清晰、故障隔离；任务简单、执行快，单实例吞吐足够。若某类任务量大，只给该类加进程即可精准扩容，不需要整体扩。

**Q2：单实例 worker 会不会重复消费同一消息？**
> 同一队列一条消息只会被一个消费者消费（竞争机制），正常不会重复。但「ACK 超时重投」「超时补偿」会让同一条消息被重复投递，即使单实例也会重复消费——所以靠幂等 + 状态机 + 分布式锁保障，与实例数量无关。

**Q3：单机部署中间件，可靠性怎么保证？**
> 本地跑通用单实例，靠 RabbitMQ 的**消息持久化 + 手动 ACK + 本地消息表重发**保证「不丢」；靠**幂等 + 状态机 + 分布式锁**保证「不重」。集群化只是把这些能力在多个节点上复制一遍，逻辑不变。

**Q4：task-center 无状态，为什么能随意扩展？**
> 因为状态都外置到了 MySQL（任务数据）和 Redis（缓存 / 锁），服务本身不存本地状态，所以加实例不会产生数据不一致，可以水平扩展。

## 九、横向扩展如何应对高并发（与实习架构对比）

| 维度 | 实习（单节点） | TaskFlow（分布式） |
|---|---|---|
| 队列位置 | 单节点集中托管 | 消息中间件（RabbitMQ），高可用 |
| 队列类型 | 写死的 4 个业务队列 | 通用队列 + 延迟队列 + 死信队列 |
| 流水线 | 硬编码「转写 → 质检」 | 可插拔 handler，任意任务类型 |
| 伸缩性 | worker 在别处，但队列单点 | worker 多进程横向扩展 |
| 可靠性 | 单节点，宕机风险高 | confirm / ACK / 持久化 / 幂等全链路保障 |
| 资源适配 | 单机内存队列 | 2 台机器即可跑通，中间件单机 |

**核心升级思想**：保留实习「多级队列 + 任务对象 + 队列与执行分离」的思想，将「单节点内存队列」升级为「分布式消息中间件」，将「单机线程池」升级为「多节点 worker 进程」。

## 十、部署架构的可观测与安全

- **全链路 traceId**：网关生成，经 Feign / 线程池透传，贯穿提交 → 入队 → 消费 → 执行 → 回写全过程，便于分布式链路定位。
- **统一入口安全**：所有流量经 Gateway，JWT 鉴权统一在网关完成，内部服务间通过内网鉴权通信。
- **限流分层**：Gateway 层（令牌桶）→ worker 消费端（prefetch）→ 线程池（有界队列），形成三级漏斗。
